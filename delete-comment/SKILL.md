# 注释四分类治理

对目标范围的全部代码注释执行六步：白名单与归宿裁决 → 全量枚举 → 四分类（附证据）→ 按类处置 → 验证对账 → 写入报告。调用即执行，不 dryrun。无法判定的注释列入存疑清单（存疑 = 证据不足、暂不处置），不删除，不阻塞整体流程。整个流程只在第 0 步的归宿裁决判不了时提问一次。

## 第 0 步：读项目约束，建白名单，裁决决策记录归宿

1. 读项目根的 CLAUDE.md / AGENTS.md / CONTRIBUTING。提取与注释相关的规则：保留注释的硬约束、注释语言约定、迁移文件注释规范、测试直接断言的注释。
2. 白名单默认项（项目规则无额外规定时仍生效）：
   - 迁移 SQL / 数据库脚本中的注释
   - 许可证与版权头
   - 测试文件中被断言直接引用的注释文本
   - 指向外部文档的指针注释（ADR、设计文档、issue、笔记均可；ADR = Architecture Decision Record，架构决策记录）
   - 项目规则显式要求的其余注释类别
3. 决策记录归宿裁决（第 3 步处置的前置判断；主动判断，判不了才问 owner）：
   - 自查两条：项目有无 `docs/adr/` 或同类 ADR 目录；项目规则有无「注释只写为什么」类约定（即注释本身就是决策记录的合法居所）。
   - 有 ADR 目录 → 走迁移（第 3 步原路径）。
   - 无 ADR 目录、有「注释=为什么居所」约定 → decision 原位保留，不迁。裁决写入报告，如实记录，供 owner 复核。
   - 无 ADR 目录、也看不出约定 → 只问 owner 一个问题：「决策类注释迁 ADR（新建最小 docs/adr/，Nygard 四段式：状态/背景/决策/后果）还是留在注释里？」给推荐答案：长期维护的项目推荐迁。理由：没有 ADR 体系时，决策注释无处可去，只会随代码改动而过期。答完即执行，不展开盘问。
   - 迁移粒度红线：只迁架构级取舍；行内「为什么」留在注释。若迁出条目预计超过几十条，说明粒度过细，先收敛到架构级再迁。
4. 白名单与归宿裁决写入项目 Temp 下的 `comment-whitelist.md`。后续轮次以它为准，不重新裁决。

## 第 1 步：全量枚举（单一事实源）

逐文件提取注释（行号、内容、所属符号），输出 TSV 到项目 Temp 下的 `comment-inventory.tsv`。后续分类、处置、对账全部以此文件为唯一依据。禁止重新 grep 出第二份数字。

枚举注意：
- 引号配平嗅探会把 XML/模板字符串字面值（含 `//` 的 fixture、命名空间声明）误收为注释。这类行标进清单无妨：分类阶段会把它们落入存疑清单。处理存疑清单时，先怀疑枚举器误收，再怀疑注释本身有问题。
- 分类代理只被允许写自己的输出 TSV。分类代理不得删除或修改任何文件，包括它们自己的中间产物。

## 第 2 步：四分类（每条附证据）

- 同义反复：注释信息与紧邻代码语义等价。证据 = 注释改写成代码事实陈述后，与代码比对的结果。
- 借口：为妥协实现辩护（hack / workaround /「暂时、后续再改」）。证据 = 注释原文 + 被指认的妥协实现位置。口径：含「接受现状 / 量级无害 / 残留由运维清 / 尽力而为 / 待清理项 / 后续一并」等辩护语的注释，即便措辞像流程描述，也归此类——它们为吞错或泄漏做免责声明。纯复述控制流的注释不算（如「失败换下一个候选」，配合法的空 catch 回退）。两处同形态注释判定不一致即口径漂移：先统一口径，再继续分类。
- 过期：注释引用的符号、行为、版本号已不存在。证据 = `git log -S <symbol>` 的关键提交哈希。拿不到 git 证据的降级为存疑。
- 决策记录：记录非显而易见的取舍与理由。证据 = 原文 + 已有 ADR 编号，或「需新建 ADR」标记。
- 存疑：证据不足的一律进存疑清单，不删。

输出契约：分类结果写 TSV，category 列只允许五个枚举值（tautology/excuse/stale/decision/suspect）。合并多批结果时必须校验 category 值域。非枚举值要映射或退回重分，不许静默漏收。

抽样门：随机抽 30 条已完成分类的注释，让一个子代理按本标准独立重分类，与主分类比对，算 Cohen's kappa。kappa < 0.7 时先修订本表表述的歧义，再重新抽样；达标才继续。目标范围不足 100 条注释时跳过此门并注明。单一类别主导时 kappa 不可定义，以一致率通过并注明。

## 第 3 步：按类处置

- 同义反复、过期：用 Edit 逐条删除（编辑代码属正常权限流程）。不做任何 rm / 整文件删除 / 数据库操作。
- 借口：删除，并为被指认的妥协实现开 issue 条目（位置、影响、修复方向），写入报告。修复不在本技能职责内。混编检查：借口注释常与决策内容同块（如「新入口一律走这里」+「旧拷贝待清理」连写三行）。整块删除前，先把块内非借口的指引信息记入 issue 条目，防信息随注释丢失。
- 决策记录：按第 0 步归宿裁决执行。迁 ADR：沿用项目既有 ADR 编号与文件惯例；无惯例的新建 `docs/adr/`，用 Nygard 四段式，被迁注释原位保留一行指向新 ADR 的指针。原位保留：裁决写入报告，供 owner 复核。
- 存疑：原样保留，列清单交 owner。

## 第 4 步：验证（全绿才报完成）

1. 行数对账：`git diff --stat` 净删行数 = 处置表「删除」类行数之和；ADR 新增文件数 = 「迁移」类条数。两式都成立才继续。注意两点：
   - 行尾注释（eol 类）删除在 diff 中表现为等量 insertions（`code // x` → `code` 计一删一增），是正常表现，不是误改。
   - 删除脚本 dry-run 时必须校验「受影响行数 > 0 且与计划行数同量级」。0 是异常信号，不能当干净放过。
2. 类型检查与全量测试：探测项目包管理器（有 pnpm-lock.yaml 用 pnpm，否则按 npm/yarn 各自约定），两侧各自跑 `tsc --noEmit` 与 `test:run`。无法运行的环境写明原因与替代检查。两侧必须各跑一次，并核对测试数符合该侧预期——防 shell 目录竞争导致一侧实际跑了另一侧的套件、误报通过。
3. 反向抽查：从已删清单随机抽 5%，人工重读。确认等价性声明成立、过期判定有 git 证据。
4. 行为等价（仅当注释涉及导入导出、编号生成等可被测试样例（fixture）钉住的语义时）：同一份样例删除前后各跑一次，产物 diff 为空。

## 第 5 步：报告与估算

报告写入 `docs/audits/YYYY-MM-DD-comment-cleanup.md`（无该目录的项目放项目根），含逐条处置表（文件、行号、类别、证据、处置）。估算给三行数字：删除行数 / 迁移条数（含 ADR 新增数）/ 白名单受保护行数。注明依据是实测枚举值。

## 边界（与其他规则的关系）

- 有的项目禁止删除既有注释（如 CLAUDE.md 的项目规则）。显式调用本技能，即视为对该约束前三类注释的授权放开；第四类按归宿裁决处理，不做删除。
- 创建 lint 规则、改 eslint / settings.json / hooks 属配置修改。本技能只产出建议文本与配置样例，不自动改配置；落地须 owner 批准。
- 清理完成后，在项目工作流内按规模走对应审查层。全库级清理建议独立审查复核后再提交。

## 停止条件

验证任一项未全绿、或对任一条目的类别不确定时，停止处置，把该条目退回存疑清单。不允许「先删了再说」。
